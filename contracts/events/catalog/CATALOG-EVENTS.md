# Контракты событий Catalog Service

## 1. Назначение

Документ описывает события Catalog Service, предназначенные для уведомления других сервисов об изменениях данных каталога.

## 2. Участники

Издатель событий — Catalog Service.

Потребители и особенности обработки указываются в описании соответствующего события.

## 3. События

### 3.1. `OfferChanged`

Сообщает об изменении данных предложения, его расписания или статуса.

Предложения физически не удаляются из Catalog Service. Их доступность определяется статусом, изменение которого передаётся в `OfferChanged`.

**Условия публикации**

Catalog Service публикует событие, когда:

- предложение впервые опубликовано;
- изменились данные предложения или его расписание;
- изменился статус предложения, включая снятие с публикации.

Данные места и его категории передаются отдельным событием `PlaceChanged`. Их изменение само по себе не вызывает публикацию `OfferChanged`. Если при этом изменяются статусы предложений, для каждого затронутого предложения публикуется `OfferChanged`.

Событие передаёт актуальный снимок данных, определённых контрактом. Частичные изменения отдельных полей не используются.

**Известные потребители**

| Потребитель | Назначение |
|---|---|
| Search Service | Обновление поисковой копии данных с учётом состояния предложения |

#### 3.1.1. Топик и ключ сообщения

| Параметр | Значение |
|---|---|
| Топик | `catalog.offers.events` |
| Ключ сообщения | `offerId` |
| Формат ключа | UUID предложения в строковом представлении |
| Формат значения | JSON, структура определяется JSON Schema |

Ключ передаётся как Kafka record key, отдельно от тела сообщения, и соответствует `offerId` в теле. Для всех событий одного предложения используется одинаковое значение ключа.

Ключ используется для распределения сообщений по партициям Kafka и организации последовательной обработки изменений одного предложения. Он не является уникальным идентификатором события и не заменяет проверку версии потребителем.

**Публикация и обработка пачками**

- Одно сообщение `OfferChanged` описывает одно предложение.
- Catalog Service может публиковать сообщения порциями, в том числе при массовом изменении статусов предложений. Каждое сообщение сохраняет собственный ключ `offerId`.
- Потребители могут получать и обрабатывать пачки сообщений с разными ключами. Версия проверяется отдельно для каждого предложения.
- Размер пачки и границы транзакций определяются реализацией публикации и обработки. Для пакетной обработки не требуется объединять несколько предложений в тело одного сообщения.

#### 3.1.2. Структура сообщения

Сообщение содержит общие поля события и объект `data` с актуальным состоянием предложения.

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `eventId` | string, UUID | Да | Идентификатор события. Создаётся один раз; при повторной отправке или доставке того же события не меняется |
| `eventType` | string | Да | Тип события: `OfferChanged` |
| `occurredAt` | string, date-time | Да | Время изменения в Catalog в формате ISO 8601, UTC, например `2026-11-08T12:30:00Z` |
| `offerId` | string, UUID | Да | Идентификатор предложения. Совпадает с Kafka record key |
| `revision` | int32 | Да | Неотрицательная версия снимка в пределах одного `offerId`. Строго увеличивается при формировании нового снимка |
| `data` | object (`OfferChangedData`) | Да | Актуальный снимок предложения. Поля объекта описаны ниже |

**Формирование `revision`**

Предлагаемый источник — `offers.event_revision` в Catalog (`int`, начальное значение `0`). Счётчик увеличивается при формировании нового снимка предложения, включая изменения расписания и статуса; при повторной отправке того же события версия не меняется. Версия места из `PlaceChanged` учитывается независимо.

**Объект `data` — `OfferChangedData`**

`object` обозначает вложенную структуру с определёнными полями. Все перечисленные поля передаются в каждом снимке, включая неактивные статусы; `null` допускается только там, где указан в типе.

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `status` | string | `ACTIVE`, `SUSPENDED`, `EXPIRED`, `ARCHIVED` |
| `placeId` | string, UUID | Идентификатор места; в Search соответствует `search_places.place_id` |
| `discountType` | string | `PERCENT`, `FIXED_AMOUNT`, `SPECIAL_PRICE`, `FREE_ITEM`, `OTHER` |
| `discountValue` | number / null | Значение скидки с точностью до двух знаков после запятой. `null` допустим для любого типа; заданное значение для `PERCENT` — больше 0 и не больше 100, для `FIXED_AMOUNT` и `SPECIAL_PRICE` — больше 0; для остальных типов — только `null` |
| `lastVerifiedAt` | string, date-time | Дата последнего подтверждения актуальности в Catalog, ISO 8601, UTC |
| `validFrom` | string, date / null | Начало срока действия, `YYYY-MM-DD`; `null` — без нижней границы |
| `validUntil` | string, date / null | Последний день действия включительно, `YYYY-MM-DD`; при заданных обеих датах не раньше `validFrom`; `null` — без верхней границы |
| `schedule` | array of `ScheduleGroup` | Полное расписание предложения. `[]` — без дополнительных ограничений по дням и часам |

**Вложенные структуры**

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `schedule[].daysOfWeek` | array of integer | Непустой массив уникальных дней: 1 — понедельник, 7 — воскресенье. Один день не повторяется в разных группах |
| `schedule[].intervals` | array of `TimeInterval` | Непустой массив интервалов для каждого дня группы, упорядоченных по началу и без пересечений |
| `schedule[].intervals[].timeFrom` | string | Начало интервала в местном времени, `HH:mm`, от `00:00` до `23:59` |
| `schedule[].intervals[].timeUntil` | string | Конец интервала в местном времени, `HH:mm`, до `24:00`; строго позже начала |

Интервалы задаются как `[timeFrom, timeUntil)`, переход через полночь разделяется на два дня. После разворачивания групп допускается не больше 28 интервалов, как в [модели Catalog](../../../data-model/DATA-MODEL.md).

`offerId` передаётся в общих полях события и в `data` не дублируется. В Search поле `schedule` сохраняется в `search_offers.schedule_preview`. Даты и расписание интерпретируются в часовом поясе места из `search_places.timezone`, полученном через `PlaceChanged`. `conditions` в этот контракт не входит.

#### 3.1.3. Обработка в Search Service

Search Service хранит в `search_offers` только предложения со статусом `ACTIVE` по последнему применённому событию Catalog.

Состояние предложения хранится в `search_sync_state` по ключу `(entity_type = 'OFFER', entity_id = offerId)`. Если состояния ещё нет, применяется первая полученная версия, включая `0`. Если `revision` меньше или равна сохранённой `revision`, событие пропускается. Для более новой версии выполняется действие, соответствующее переданному статусу:

| Статус предложения | Действие Search Service |
|---|---|
| `ACTIVE` | Создать или обновить запись в `search_offers`, связав её с местом по `placeId` |
| `SUSPENDED`, `EXPIRED`, `ARCHIVED` | Удалить запись из `search_offers`, исключив предложение из списка и карты |

Если для активного предложения место ещё не получено через `PlaceChanged`, событие надёжно откладывается до появления места и не отмечается применённым. Неактивное предложение обрабатывается независимо от наличия места.

Состояние в `search_sync_state` сохраняется вместе с последней применённой версией: для активного предложения — `is_deleted = false`, для исключённого из поиска — `is_deleted = true`. Этот флаг относится к поисковой копии и не означает физического удаления предложения из Catalog. Строка места в `search_places` не изменяется.

Проверка версии, изменение `search_offers` и запись состояния выполняются одной транзакцией с защитой от конкурентной обработки. Обработка сообщения подтверждается в Kafka после commit.

#### 3.1.4. Схема и совместимость

Структура сообщения описывается JSON Schema. Версии схемы управляются через Schema Registry; идентификатор схемы передаётся механизмом сериализации. Отдельное поле `schemaVersion` в теле не используется. Поле `revision` относится к данным предложения и не зависит от версии схемы.

- **Сериализация.** Издатель и потребители используют JSON Schema сериализатор и десериализатор, совместимые с выбранным Registry.
- **Режим совместимости — `BACKWARD_TRANSITIVE`.** Новая схема должна позволять читать сообщения всех предыдущих зарегистрированных версий. При обновлении сначала развёртываются потребители, затем издатель.
- **Изменения схемы.** Перед регистрацией новой версии проверяется совместимость в Registry. Изменение смысла полей и значений согласуется отдельно: проверка схемы не гарантирует совместимость бизнес-логики.
- **Несовместимые изменения.** Требуют отдельного согласования и плана перехода потребителей.

#### 3.1.5. Пример сообщения

Топик: `catalog.offers.events`. Ключ: `36b91b96-bcbc-4c53-8a33-7773ff60888c`.

Тело сообщения после десериализации:

```json
{
  "eventId": "befa686a-9ed9-496c-bb9d-456d615f1b40",
  "eventType": "OfferChanged",
  "occurredAt": "2026-11-16T12:30:00Z",
  "offerId": "36b91b96-bcbc-4c53-8a33-7773ff60888c",
  "revision": 3,
  "data": {
    "status": "ACTIVE",
    "placeId": "e74cdfc2-3a53-43b1-aef1-d027a95d51f3",
    "discountType": "PERCENT",
    "discountValue": 15,
    "lastVerifiedAt": "2026-11-16T12:00:00Z",
    "validFrom": "2026-11-01",
    "validUntil": null,
    "schedule": [
      {
        "daysOfWeek": [1, 2, 3, 4, 5],
        "intervals": [
          { "timeFrom": "10:00", "timeUntil": "14:00" }
        ]
      }
    ]
  }
}
```

### 3.2. `PlaceChanged`

Сообщает об изменении данных места, включая его категорию и часовой пояс.

**Условия публикации**

Catalog Service публикует событие, когда:

- место впервые опубликовано вместе с предложением;
- изменились название, город, адрес, координаты, часовой пояс или категория места;
- изменилось название связанной категории.

При изменении названия категории публикуется отдельное событие для каждого затронутого места. Массовая публикация выполняется порциями; одно сообщение описывает одно место и сохраняет собственный ключ `placeId`.

Событие передаёт полный актуальный снимок данных, определённых контрактом. Данные и статусы предложений передаются через `OfferChanged`.

**Известные потребители**

| Потребитель | Назначение |
|---|---|
| Search Service | Обновление общих данных места для поиска, карты и карточек |

#### 3.2.1. Топик и ключ сообщения

| Параметр | Значение |
|---|---|
| Топик | `catalog.places.events` |
| Ключ сообщения | `placeId` |
| Формат ключа | UUID места в строковом представлении |
| Формат значения | JSON, структура определяется JSON Schema |

Ключ передаётся как Kafka record key, отдельно от тела сообщения, и соответствует `placeId` в теле. Для всех событий одного места используется одинаковый ключ. Версия проверяется отдельно для каждого места, в том числе при обработке пачками.

#### 3.2.2. Структура сообщения

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `eventId` | string, UUID | Да | Идентификатор события. При повторной отправке или доставке того же события не меняется |
| `eventType` | string | Да | Тип события: `PlaceChanged` |
| `occurredAt` | string, date-time | Да | Время изменения в Catalog в формате ISO 8601, UTC |
| `placeId` | string, UUID | Да | Идентификатор места. Совпадает с Kafka record key |
| `revision` | int32 | Да | Неотрицательная версия снимка в пределах одного `placeId`. Строго увеличивается при формировании нового снимка |
| `data` | object (`PlaceChangedData`) | Да | Актуальный снимок места |

**Формирование `revision`**

Предлагаемый источник — `places.event_revision` в Catalog (`int`, начальное значение `0`). Счётчик увеличивается при формировании нового снимка места, включая изменение названия категории; при повторной отправке того же события версия не меняется. Версии предложений из `OfferChanged` учитываются независимо.

**Объект `data` — `PlaceChangedData`**

Все перечисленные поля обязательны и не допускают `null`.

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `placeName` | string | Название места, до 200 символов, непустое после удаления пробелов по краям |
| `city` | string | Город, до 100 символов, непустое после удаления пробелов по краям |
| `addressLine` | string | Адрес без города, до 300 символов, непустое после удаления пробелов по краям |
| `location` | object (`Location`) | Координаты места WGS 84; структура ниже |
| `categoryCode` | string | Код категории, до 50 символов, формат `^[a-z][a-z0-9_]*$` |
| `categoryName` | string | Название категории, до 100 символов |
| `timezone` | string | Действующий идентификатор часового пояса IANA, до 64 символов, например `Europe/Moscow` |

**Вложенная структура `Location`**

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `latitude` | number | Обязательное; широта от −90 до 90 |
| `longitude` | number | Обязательное; долгота от −180 до 180 |

`placeId` передаётся в общих полях события и в `data` не дублируется. В Search координаты преобразуются в `search_places.location`, а `search_vector` формируется локально из названия и адреса.

#### 3.2.3. Обработка в Search Service

Состояние места хранится в `search_sync_state` по ключу `(entity_type = 'PLACE', entity_id = placeId)`.

| Условие | Действие Search Service |
|---|---|
| Состояния ещё нет | Создать `search_places` и сохранить первую полученную версию, включая `0` |
| Входящая `revision` ≤ сохранённой | Пропустить событие без изменения данных и состояния |
| Входящая `revision` больше сохранённой | Обновить `search_places` и сохранить новую версию |

Проверка версии, запись места и состояния выполняются одной транзакцией с защитой от конкурентной обработки. В состоянии сохраняются `is_deleted = false` и время применения `applied_at`; обработка сообщения подтверждается в Kafka после commit.

Строки `search_offers` не изменяются. Место сохраняется даже без активных предложений, но в выдачу попадает только при наличии подходящего предложения.

Порядок обработки между топиками мест и предложений не гарантируется. После сохранения места отложенные `OfferChanged` для него обрабатываются повторно с проверкой версии предложения.

#### 3.2.4. Схема и совместимость

Для `PlaceChanged` используется отдельная JSON Schema в Schema Registry с режимом `BACKWARD_TRANSITIVE`. Поле `schemaVersion` в теле не используется; `revision` обозначает версию данных места.

Сериализация, проверка совместимости и порядок обновления сервисов соответствуют [правилам `OfferChanged`](#314-схема-и-совместимость).
