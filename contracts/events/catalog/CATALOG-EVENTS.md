# Контракты событий Catalog Service

## 1. Назначение

Документ описывает события Catalog Service, предназначенные для уведомления других сервисов об изменениях данных каталога.

## 2. Участники

Издатель событий — Catalog Service.

Потребители и особенности обработки указываются в описании соответствующего события.

## 3. События

### 3.1. `CatalogChanged`

Передаёт актуальные снимки места и предложений, данные которых изменились.

**Условия публикации**

| Что изменилось | Что передаёт Catalog |
|---|---|
| Место впервые опубликовано | `place` и `offers` с первыми опубликованными предложениями |
| Изменились данные места, включая название связанной категории | `place` |
| На существующем месте добавили предложение, изменили его данные, расписание или статус | `offers` с затронутыми предложениями |
| Вместе изменились данные места и предложений | `place` и `offers` с затронутыми предложениями |

Каждый переданный снимок содержит все поля, описанные контрактом. Если данные снимков остались прежними, событие не публикуется.

**Известные потребители**

| Потребитель | Назначение |
|---|---|
| Search Service | Обновление поисковой копии данных для списка, карты и карточек |

#### 3.1.1. Топик и ключ сообщения

| Параметр | Значение |
|---|---|
| Топик | `catalog.search.events` |
| Ключ сообщения | `placeId` |
| Формат ключа | UUID места в строковом представлении |
| Формат значения | JSON, структура определяется JSON Schema |

Kafka record key передаётся отдельно от тела и совпадает с `placeId` в теле. События одного места направляются в одну партицию по этому ключу. Catalog публикует первое событие места раньше последующих изменений, а Search обрабатывает сообщения последовательно в пределах партиции.

**Публикация и обработка пачками**

Одно сообщение относится к одному месту и может содержать несколько его предложений. При массовом изменении, например переименовании категории, Catalog публикует отдельное сообщение для каждого затронутого места. Сообщения можно отправлять и читать пачками.

#### 3.1.2. Структура сообщения

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `eventId` | string, UUID | Да | Идентификатор события. Сохраняется при повторной отправке того же сообщения |
| `eventType` | string | Да | Тип события: `CatalogChanged` |
| `occurredAt` | string, date-time | Да | Время изменения в Catalog в формате ISO 8601, UTC |
| `placeId` | string, UUID | Да | Идентификатор места. Совпадает с Kafka record key |
| `data` | object (`CatalogChangedData`) | Да | Снимок места, снимки предложений или оба блока |

**Объект `data` — `CatalogChangedData`**

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `place` | object (`PlaceSnapshot`) | Снимок места, указанного в `placeId` |
| `offers` | array of `OfferSnapshot` | Непустой массив снимков затронутых предложений этого места. Каждый `offerId` встречается один раз |

В `data` должен присутствовать хотя бы один из блоков. Отсутствие блока оставляет соответствующие данные без изменений. Предложения, которых нет в `offers`, остаются без изменений. Снятие с публикации передаётся через `status` предложения.

**Формирование `revision`**

У места и каждого предложения свой счётчик версий. Предлагаемый источник — `places.event_revision` и `offers.event_revision` в Catalog (`int`, начальное значение `0`). При изменении снимка увеличивается только версия соответствующей сущности. Это касается и изменений связанных данных снимка, например названия категории места или расписания предложения.

Catalog сохраняет изменения, версии и готовое сообщение в outbox одной транзакцией. При повторной отправке сохраняются `eventId`, тело и все версии.

**Снимок места — `PlaceSnapshot`**

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `revision` | int32 | Неотрицательная версия снимка в пределах одного `placeId` |
| `placeName` | string | Название места, до 200 символов, непустое после удаления пробелов по краям |
| `city` | string | Город, до 100 символов, непустое после удаления пробелов по краям |
| `addressLine` | string | Адрес без города, до 300 символов, непустое после удаления пробелов по краям |
| `location` | object (`Location`) | Координаты места WGS 84 |
| `categoryCode` | string | Код категории, до 50 символов, формат `^[a-z][a-z0-9_]*$` |
| `categoryName` | string | Название категории, до 100 символов |
| `timezone` | string | Идентификатор часового пояса IANA, до 64 символов, например `Europe/Moscow` |

**Снимок предложения — `OfferSnapshot`**

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `offerId` | string, UUID | Идентификатор предложения |
| `revision` | int32 | Неотрицательная версия снимка в пределах одного `offerId` |
| `status` | string | `ACTIVE`, `SUSPENDED`, `EXPIRED`, `ARCHIVED` |
| `discountType` | string | `PERCENT`, `FIXED_AMOUNT`, `SPECIAL_PRICE`, `FREE_ITEM`, `OTHER` |
| `discountValue` | number / null | Значение скидки с точностью до двух знаков после запятой. `null` допустим для любого типа. Заданное значение для `PERCENT` — больше 0 и не больше 100, для `FIXED_AMOUNT` и `SPECIAL_PRICE` — больше 0. Для остальных типов допустим только `null` |
| `lastVerifiedAt` | string, date-time | Дата последнего подтверждения актуальности в Catalog, ISO 8601, UTC |
| `validFrom` | string, date / null | Начало срока действия, `YYYY-MM-DD`. `null` — без нижней границы |
| `validUntil` | string, date / null | Последний день действия включительно, `YYYY-MM-DD`. При заданных обеих датах не раньше `validFrom`. `null` — без верхней границы |
| `schedule` | array of `ScheduleGroup` | Полное расписание предложения. `[]` — без дополнительных ограничений по дням и часам |

Все поля переданного снимка обязательны. `null` допускается только там, где указан в типе. Все предложения в сообщении связаны с `placeId` из общих полей.

**Вложенные структуры**

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `location.latitude` | number | Широта от −90 до 90 |
| `location.longitude` | number | Долгота от −180 до 180 |
| `schedule[].daysOfWeek` | array of integer | Непустой массив уникальных дней: 1 — понедельник, 7 — воскресенье. Один день не повторяется в разных группах |
| `schedule[].intervals` | array of `TimeInterval` | Непустой массив интервалов для каждого дня группы. Интервалы упорядочены по началу и не пересекаются |
| `schedule[].intervals[].timeFrom` | string | Начало интервала в местном времени, `HH:mm`, от `00:00` до `23:59` |
| `schedule[].intervals[].timeUntil` | string | Конец интервала в местном времени, `HH:mm`, до `24:00`. Строго позже начала |

Поля вложенных структур обязательны. Интервалы задаются как `[timeFrom, timeUntil)`. Переход через полночь разделяется на два дня. После разворачивания групп допускается до 28 интервалов, как в [модели Catalog](../../../data-model/DATA-MODEL.md).

#### 3.1.3. Обработка в Search Service

Search сравнивает версии отдельно для места и каждого предложения в `search_sync_state`. Ключ места — `('PLACE', placeId)`, ключ предложения — `('OFFER', offerId)`. При отсутствии состояния можно применить любую первую версию, включая `0`. Снимки с версией меньше или равной сохранённой пропускаются. Остальные снимки из того же сообщения обрабатываются.

| Снимок | Действие Search Service |
|---|---|
| Место | Создать или обновить `search_places`. Сохранить состояние с `is_deleted = false` |
| Предложение со статусом `ACTIVE` | Создать или обновить `search_offers`, связав запись с местом по `placeId`. Сохранить состояние с `is_deleted = false` |
| Предложение со статусом `SUSPENDED`, `EXPIRED` или `ARCHIVED` | Удалить запись из `search_offers`. Сохранить состояние с `is_deleted = true` |

Search сначала применяет снимок места, затем снимки предложений. Проверка версий, запись данных и обновление состояния выполняются одной транзакцией с защитой от конкурентной обработки. Для каждого применённого снимка сохраняются `revision` и `applied_at`. Обработка сообщения подтверждается в Kafka после commit. Если для активного предложения место отсутствует, обработка сообщения завершается ошибкой для повторной попытки.

Координаты сохраняются в `search_places.location`, а `search_vector` формируется из названия и адреса. `schedule` сохраняется в `search_offers.schedule_preview`. Даты и расписание интерпретируются в часовом поясе места. Место сохраняется при отсутствии активных предложений и попадает в выдачу при наличии подходящего предложения.

#### 3.1.4. Схема и совместимость

Структура сообщения описывается JSON Schema. Schema Registry управляет версиями схемы, а сериализатор передаёт её идентификатор. Поле `schemaVersion` в теле отсутствует. `revision` обозначает версию данных места или предложения.

- **Сериализация.** Издатель и потребители используют сериализатор и десериализатор JSON Schema, совместимые с Registry.
- **Режим совместимости — `BACKWARD_TRANSITIVE`.** Обновлённый потребитель должен читать сообщения всех предыдущих зарегистрированных версий схемы. При обновлении сначала развёртываются потребители, затем издатель.
- **Изменения схемы.** Совместимость проверяется в Registry перед регистрацией новой версии. Изменения смысла полей и несовместимые изменения согласуются с потребителями отдельно.
