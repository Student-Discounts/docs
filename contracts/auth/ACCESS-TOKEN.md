# Контракт access-токена и проверки прав

## 1. Назначение

Документ описывает, какой токен выпускает сервис auth, как его проверяют остальные сервисы, какие права дают роли и в каком формате сервис отвечает `401` и `403`.

Издатель токена — auth. Потребители — все сервисы с защищёнными endpoint: submission, moderation, media, catalog и search, если у них появятся закрытые операции.

## 2. Как сервис проверяет токен

Клиент передаёт токен в заголовке `Authorization: Bearer <token>`. Шлюз Kong передаёт заголовок сервису без изменений и токен не проверяет. Поэтому каждый сервис проверяет токен сам, локально, без запроса в auth на каждый вызов.

Сервис отклоняет токен с ответом `401`, если не выполнено хотя бы одно условие:

| Проверка | Значение |
|---|---|
| Подпись | RS256, ключ из JWKS auth по `kid` из заголовка токена |
| `iss` | Совпадает с настроенным адресом auth |
| `aud` | Содержит `student-discounts-api` |
| `exp` | Срок не истёк |
| `sub`, `sid` | Строки в формате UUID |
| `roles` | Массив строк |

Ключи публикуются по адресу `GET /.well-known/jwks.json`. Сервис загружает их напрямую из auth, не через шлюз, и кэширует. При появлении неизвестного `kid` ключи загружаются заново, поэтому смена ключа не требует перезапуска сервисов.

Настройка Spring Boot Resource Server:

```properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=${SD_AUTH_ISSUER:http://localhost:8080}
spring.security.oauth2.resourceserver.jwt.jwk-set-uri=${SD_AUTH_JWK_SET_URI:http://localhost:8080/.well-known/jwks.json}
spring.security.oauth2.resourceserver.jwt.audiences=student-discounts-api
```

`jwk-set-uri` нужно указать явно: auth не публикует `/.well-known/openid-configuration`, и без этого параметра Spring при старте попытается его загрузить. Значение `issuer-uri` должно совпадать с переменной `SD_AUTH_ISSUER`, с которой запущен auth, а не с адресом, по которому сервис до него достучался.

## 3. Структура токена

| Claim | Тип | Описание |
|---|---|---|
| `iss` | string | Адрес auth из `SD_AUTH_ISSUER` |
| `aud` | string или string[] | `student-discounts-api`. При одном значении приходит строкой, обе формы допустимы по RFC 7519 |
| `sub` | string, UUID | Идентификатор пользователя. Другие сервисы хранят его как `author_id`, `moderator_id` и т. п. Email и имя в токен не входят |
| `sid` | string, UUID | Идентификатор сессии |
| `iat`, `exp` | number | Время выпуска и окончания срока в секундах Unix. Срок жизни 5 минут |
| `roles` | string[] | Роли пользователя из раздела 4 |
| `org_ids` | string[], UUID | Организации, в которых членство представителя подтверждено. Пока не выпускается, потребители считают список пустым |

Пример:

```json
{
  "iss": "http://localhost:8080",
  "aud": "student-discounts-api",
  "sub": "8d1f6c2e-3b4a-4f0e-9a51-2c7e5d9b1a00",
  "sid": "b3e1c9d0-7f2a-4c11-8e6b-0a9d4f3c2e17",
  "iat": 1792573200,
  "exp": 1792573500,
  "roles": ["STUDENT", "MODERATOR"]
}
```

Разрешений в токене нет: каждый сервис вычисляет их из `roles` по таблице раздела 5. Поэтому изменение таблицы не требует перевыпуска токенов.

## 4. Роли

| Роль | Как получить |
|---|---|
| `STUDENT` | Автоматически при регистрации |
| `ORG_REPRESENTATIVE` | При подтверждённом членстве в организации. Выдача пока не реализована |
| `MODERATOR` | Назначает старший модератор |
| `SENIOR_MODERATOR` | Только начальными данными при запуске auth, через API не выдаётся |

У пользователя может быть несколько ролей, права суммируются. Неизвестные значения в `roles` сервис пропускает, а не отклоняет токен: так добавление новой роли не ломает сервисы, которые о ней ещё не знают.

## 5. Права ролей

Endpoint защищается разрешением, а не ролью: `@PreAuthorize("hasAuthority('MODERATION_DECIDE')")`. Тогда изменение состава роли — это правка одной таблицы, а не кода всех сервисов.

| Разрешение | Действие | Проверяет | `STUDENT` | `ORG_REPRESENTATIVE` | `MODERATOR` | `SENIOR_MODERATOR` |
|---|---|---|:-:|:-:|:-:|:-:|
| `SUBMISSION_CREATE` | Создать заявку, предложить изменение карточки | submission | ✓ | ✓ | | |
| `SUBMISSION_READ_OWN` | Видеть свои заявки | submission | ✓ | ✓ | | |
| `SUBMISSION_EDIT_OWN` | Редактировать свой черновик или доработку | submission | ✓ | ✓ | | |
| `SUBMISSION_CANCEL_OWN` | Отозвать свою заявку | submission | ✓ | ✓ | | |
| `MEDIA_UPLOAD` | Загрузить фото и подтверждения | media | ✓ | ✓ | | |
| `REPORT_CREATE` | Подать жалобу | moderation | ✓ | ✓ | | |
| `ORG_MEMBERSHIP_REQUEST` | Запросить связь с организацией | auth | ✓ | ✓ | | |
| `ORG_CHANGE_PROPOSE` | Предложить изменение от имени организации | submission | | ✓ | | |
| `MODERATION_QUEUE_READ` | Видеть очередь модерации | moderation | | | ✓ | ✓ |
| `MODERATION_TAKE` | Взять заявку в работу | moderation | | | ✓ | ✓ |
| `MODERATION_DECIDE` | Одобрить, отклонить, вернуть на доработку | moderation | | | ✓ | ✓ |
| `MODERATION_ESCALATE` | Эскалировать старшему модератору | moderation | | | ✓ | ✓ |
| `REPORT_REVIEW` | Рассмотреть жалобу, приостановить карточку | moderation | | | ✓ | ✓ |
| `MODERATION_AUDIT_READ` | Видеть аудит модерации и историю автора | moderation | | | ✓ | ✓ |
| `ORG_MEMBERSHIP_VERIFY` | Подтвердить или отклонить связь с организацией | auth | | | ✓ | ✓ |
| `MODERATION_ESCALATED_DECIDE` | Решить эскалированную заявку, переназначить заявку | moderation | | | | ✓ |
| `ROLE_MODERATOR_MANAGE` | Назначить или снять роль модератора | auth | | | | ✓ |
| `ACCOUNT_BLOCK` | Заблокировать или разблокировать аккаунт | auth | | | | ✓ |
| `SESSION_REVOKE_ANY` | Завершить сессии другого пользователя | auth | | | | ✓ |
| `IDENTITY_AUDIT_READ` | Видеть историю ролей и блокировок | auth | | | | ✓ |
| `USER_READ_ANY` | Найти пользователя по email или id | auth | | | | ✓ |

Без токена доступны вход, регистрация, обновление токена, JWKS, чтение опубликованного каталога и поиск. Все остальные endpoint требуют токен, даже если отдельного разрешения у них нет.

Разрешение открывает действие, но не объект. Условия на конкретный объект сервис проверяет сам после его загрузки:

- автор работает только со своими заявками и файлами;
- черновик редактируется только в статусах `DRAFT` и `CHANGES_REQUESTED`;
- модератор не принимает решение по своей заявке и по заявке, назначенной другому модератору;
- представитель действует только от имени организации из `org_ids`;
- старший модератор не меняет свои роли и не блокирует себя.

Эталонная реализация таблицы — `RolePermissions` и `JwtAuthorities` в пакете `authz` сервиса auth.

## 6. Актуальность прав

Access-токен живёт 5 минут и после выпуска не отзывается. Поэтому снятие роли и блокировка доходят до сервисов с задержкой до 5 минут:

- при блокировке auth сразу завершает все сессии пользователя, и новый access-токен он получить не сможет;
- при снятии роли сессии сохраняются, но при обновлении токена auth берёт роли из базы, поэтому следующий токен выйдет уже без снятой роли;
- уже выданный access-токен действует до своего `exp`.

Для обычных операций эта задержка допустима. Если для решений модерации её окажется недостаточно, auth добавит внутренний endpoint проверки актуальных ролей, и moderation будет вызывать его перед решением. Это отдельная договорённость, сейчас такого endpoint нет.

## 7. Ответы 401 и 403

Ошибки возвращаются в формате RFC 9457, `Content-Type: application/problem+json`. Клиент ориентируется на поле `code`, текст `detail` может меняться.

| Статус | Когда | `code` |
|---|---|---|
| `401` | Токена нет, он просрочен, подпись или claims не прошли проверку | `unauthorized` |
| `403` | Токен действителен, но нужного разрешения нет | `access_denied` |
| `403` | Разрешение есть, но не выполнено условие на объект | Код сервиса, например `self_management_forbidden` |
| `404` | Объект чужой и закрытый | Код сервиса. `404` вместо `403`, чтобы не раскрывать, что объект существует |

При `401` сервис также возвращает заголовок `WWW-Authenticate: Bearer`, его выставляет Spring Security.

Пример:

```json
{
  "type": "about:blank",
  "title": "Unauthorized",
  "status": 401,
  "detail": "Нужен действующий access-токен",
  "instance": "/api/v1/me",
  "code": "unauthorized"
}
```

Получив `401`, клиент один раз обновляет токены через `POST /api/v1/auth/refresh` и повторяет запрос. При `403` повторять запрос бессмысленно.

Ответы самого шлюза (`404` для неизвестного пути, `413` и `429`) идут в формате Kong `{"message": "..."}`, а не problem+json. Клиент отличает их по статусу.

## 8. Логи и корреляция

- Токен и заголовок `Authorization` не пишутся в логи. Для отладки достаточно `sub` и `sid`.
- Отказ в доступе логируется с `sub`, действием, объектом и `X-Correlation-ID`.
- Шлюз принимает `X-Correlation-ID` из `[A-Za-z0-9._-]{1,64}`, другое значение заменяет на UUID и передаёт сервису. Сервис возвращает тот же заголовок в ответе и передаёт его в вызовы других сервисов.

## 9. Обязательные тесты потребителя

| Сценарий | Ожидаемый результат |
|---|---|
| Защищённый endpoint без токена | `401`, `code: unauthorized` |
| Токен с чужим `iss`, без `aud` `student-discounts-api`, просроченный или с подписью чужим ключом | `401` |
| Токен без нужного разрешения, например студент открывает очередь модерации | `403`, `code: access_denied` |
| Токен с неизвестной ролью рядом с известной | Права известной роли работают |
| Чужой закрытый объект | `404` |

Для тестов сервис выпускает токены сам: генерирует пару ключей RSA, отдаёт открытый ключ как JWKS и подписывает токены с нужными `roles`. Пример — `SubmissionSmoke` в submission.

## 10. Версия и совместимость

Версия контракта 1.

- Добавление claim и новой роли — совместимое изменение, потребители игнорируют незнакомое.
- Удаление или переименование claim, изменение `aud` и алгоритма подписи — несовместимое. Оно согласуется со всеми потребителями заранее и повышает версию контракта.
